# `backend/api` — Service Schema

**What this document is:** a current-state map of the NestJS service in
`backend/api` itself — its modules, its own Drizzle schema files, its auth/
guard model, and its full REST surface. This is the counterpart to
[`backend/db/APP_SCHEMA.md`](../db/APP_SCHEMA.md), which documents the
Postgres `app` schema (the data). This file documents the *code* that reads
and writes that data, plus the small `backend` Postgres schema this service
owns outright for its own session/idempotency concerns.

Regenerate by re-reading `src/modules/*` and `src/db/schema/*` — there is no
tool for this one (unlike `app_schema.sql`, which is machine-generated by
`backend/db/dump_app_schema.dart`), because a NestJS module tree doesn't
introspect the way a live database does. Keep it in sync by hand when a
module, route, or schema file is added or renamed.

## 1. Two schemas, two owners

| Postgres schema | Owned by | Defined in | Canonical doc |
| --- | --- | --- | --- |
| `app` | The whole product (member apps, `shieldweb`, agent app, and this service) | `backend/db/app_schema.sql` (machine-generated) | [`backend/db/APP_SCHEMA.md`](../db/APP_SCHEMA.md) |
| `backend` | This service alone | `src/db/schema/backend-auth.ts`, `backend-idempotency.ts` | this file, §4 |

`backend/api` is not the only writer of `app` — `shieldweb` still talks to
`app` directly over SQL (`@/lib/db`) for older modules, and the Flutter apps
read `app` through this service for newer ones (see
`backend/docs/erd.md` for the historical rationale; that doc predates this
service's build-out and is now stale on its "precondition" section — the
drift it describes has since been resolved by the `app_schema.sql`
regeneration). This service never forks or duplicates the `app` DDL; it only
maps a subset of it with Drizzle for type-safe querying (§3).

## 2. Module map

internal shape: a `*.module.ts` wiring file, a `dto.ts` of Zod schemas, one
`*.service.ts` with the business logic, and the HTTP surface split across a
`member-*.controller.ts` (member-app-facing, under `v1/member/...`) and a
`staff-*.controller.ts` (`shieldweb`-facing, under `v1/staff/...`) where both
audiences exist for that domain.

## 4. The `backend` schema (this service's own tables)

Deliberately separate from `app` — service-owned session/idempotency state,
not product domain data.

| Table | Purpose | Key columns |
| --- | --- | --- |
| `backend.auth_session` | One row per active login, member or staff | `id`, `subject_type` (`MEMBER`/`STAFF`), `subject_id`, `issued_at`, `expires_at`, `revoked_at`, `user_agent`, `ip` |
| `backend.refresh_token` | Rotatable refresh token, one active per session | `id`, `session_id` → `auth_session.id` (cascade), `token_hash`, `expires_at`, `used_at` |
| `backend.idempotency_key` | Dedupes retried mutating requests (checkout, wallet redeem, agent withdrawal, lab bill collection — see `common/idempotency/idempotency.service.ts`) | `key`, `session_id`, `endpoint`, `response_snapshot` (jsonb, null while in flight), unique on `(key, endpoint)` |

`backend/docs/erd.md` §3 additionally specs a `backend.audit_log` table —
that table does **not** exist yet; it was planned but never implemented.
Treat it as a future addition, not current state, until a schema file for it
actually appears here.

Access-token / refresh-token lifecycle: `token.service.ts` issues a
short-lived JWT access token (verified per-request, never hits the DB) and a
long-lived opaque refresh token (hashed, stored in `refresh_token`, rotated
on use). `shieldweb`'s client-side counterpart (`AuthContext.tsx`/`api.ts`)
retries a 401 exactly once by calling `POST /v1/staff/auth/refresh` before
giving up — see `backend/docs/api-spec.md` for the wire format.

## 5. Auth / role model

Two independent subject types, set by `common/guards/auth.guard.ts` after
verifying the access token and attached to the request as `RequestSubject`
(`session.types.ts`):

- **MEMBER** — the shopper/patient apps. No roles; `@RequireMember()`
  (`common/decorators/require-role.decorator.ts`) is the only gate. A second
  decorator, `@RequireRegistered()` (`common/guards/registered.guard.ts`),
  additionally requires the member to have finished registration, answering
  403 `REGISTRATION_REQUIRED` otherwise.
- **STAFF** — `shieldweb`, scoped by `app.admin_role`:
  `SUPERADMIN`, `ADMIN`, `PHARMACY`, `LAB`, `APPOINTMENTS`, `DELIVERY`,
  `LAB_TECHNICIAN`. `@RequireStaff()` accepts any of these (any valid staff
  session); `@RequireRole('X', 'Y', ...)` narrows to specific roles.
  `LAB`/`PHARMACY`/`DELIVERY`/`LAB_TECHNICIAN` are additionally **branch-
  scoped** (`RequestSubject.storeId`) — `LAB`/`PHARMACY` work at a single
  store, `LAB_TECHNICIAN` likewise (added for the lab-bill/collection flow),
  `DELIVERY` is store-bound in `shieldweb`'s permission config but not
  route-enforced the same way. `SUPERADMIN`/`ADMIN` are unscoped.

Both subject types share one `backend.auth_session` table, disambiguated by
`subject_type` — deliberately, since `app.users.id` and `app.admin_user.id`
are independent sequences and could otherwise collide (see the comment on
`RequireStaff()` in `require-role.decorator.ts`, which exists specifically to
stop a member session from being resolved against the wrong table).

`@Public()` (`common/decorators/public.decorator.ts`) marks a route as
exempt from `AuthGuard` entirely — used only for `v1/public/*` and
`health.controller.ts`.

## 6. REST surface

Every route below is prefixed `/v1` except `health.controller.ts`'s. Guard
column shows the narrowest decorator actually applied (a bare `staff` means
`@RequireStaff()` — any role; a role list means `@RequireRole(...)` narrowed
below the controller's class-level guard).

  `/states/:id/districts`, `/districts/:id/assemblies`,

  `/lab-packages/:id`, `/clinics`, `/clinics/:id`, `/dietitians`

## 7. Validation and idempotency patterns

- Every mutating endpoint validates its body against a Zod schema in that
  module's `dto.ts`, applied via `common/pipes/zod-validation.pipe.ts` — not
  `class-validator`. Keep new DTOs in this style for consistency.
- Side-effecting, retriable writes (checkout, wallet redeem, agent
  withdrawal, lab bill collection) accept an idempotency key via
  `common/decorators/idempotency-key.decorator.ts` and route through
  `common/idempotency/idempotency.service.ts` (reserve-then-complete against
  `backend.idempotency_key`, see §4) rather than a plain check-then-insert.
- `common/guards/per-subject-throttler.guard.ts` rate-limits per
  authenticated subject (not per IP) — see `common/throttle.ts` for the
  configured windows.
- `common/filters/http-exception.filter.ts` normalizes every thrown error to
  one JSON error shape; see `backend/docs/api-spec.md` for the wire format
  and the member/staff error-code catalogue.
